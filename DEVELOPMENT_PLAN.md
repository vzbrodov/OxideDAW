### Первый рабочий цикл (история)

Реализован исходный код первого CLI-прототипа:

- `oxide-dsp::sample`: декодирование файла в interleaved f32 вне аудиопотока, проверка mono/stereo и неизменности формата.
- Включён флаг `pcm` Symphonia для PCM WAV.
- `oxide-audio::playback`: перечисление устройств, выбор по имени, default output config, f32/i16/u16, громкость, простая линейная интерполяция частоты, тишина после окончания файла.
- CLI: `devices`, `play <file.wav> [volume] [device name]`, остановка по Enter, ненулевой код при ошибке.
- Callback не декодирует файлы и не выделяет память; ошибку потока передаёт через atomic flag.
- Добавлен unit test интерполяции mono и тишины после конца; README содержит команды запуска и зависимости Linux.

## Цель первого продукта

Небольшая законченная DAW для семплов и паттернов с единым API действий для интерфейса и AI.

Сценарий MVP: открыть приложение → загрузить несколько WAV → собрать ритм → сделать короткую аранжировку → сохранить и повторно открыть проект → экспортировать WAV. AI может изменить паттерн, пользователь может отменить изменение одним действием.

Универсальная студия остаётся долгосрочной целью. Полноценная запись, несколько форматов внешних плагинов, собственный SDK, модульный patcher и скрипты не входят в первый MVP.

## Этапы и критерии готовности

| Этап | Содержание | Критерий завершения |
| --- | --- | --- |
| 1. Звуковой прототип | Выбор устройства, WAV, громкость, start/stop, диагностика ошибок | Стабильное воспроизведение на выбранной основной платформе |
| 2. Музыкальное ядро | Транспорт, BPM, loop, события внутри аудиоблока, полифония семплера | Паттерн играет без накопления временного дрейфа |
| 3. Модель проекта | Дорожки, паттерны, клипы, медиа, команды, undo/redo | Сохранение и загрузка восстанавливают музыкальное состояние |
| 4. Первый UI | Браузер семплов, step sequencer, транспорт, простой микшер | Ритм можно собрать без редактирования файлов |
| 5. Законченный MVP | Простой arranger, WAV export, автосохранение, отсутствующие файлы | Небольшой трек можно создать, закрыть, открыть и экспортировать |
| 6. AI-сценарий | Чтение состояния, изменение паттернов, пакетные команды | Изменения агента видны в UI и отменяются одним действием |

Небольшой MCP-прототип проверить уже после появления команд редактирования, не откладывая проверку идеи AI до завершения всего UI.

## Архитектурные ориентиры

- **Единые команды UI и MCP.** Создание дорожек, изменение нот и микшера проходят через общую валидацию и историю отмены.
- **Разделение проекта и движка.** Редактируемая модель предназначена для UI и хранения; аудиопоток получает подготовленные данные воспроизведения.
- **Ограничения real-time.** Декодирование, сеть, логирование, выделение памяти и блокирующие операции вынести из аудиообработки. Rust сам по себе не гарантирует отсутствие срывов; нужны измерения. Продумать также освобождение памяти вне аудиопотока и поведение при переполнении очередей.
- **Единое музыкальное время.** Определить ticks, доли, samples и поведение seek, loop, смены BPM. События должны размещаться точно внутри блока.
- **Надёжное хранение.** Версия формата, устойчивые ID, относительные пути медиа, атомарное сохранение и восстановление после сбоя.
- **Контролируемые действия AI.** Пакет применяется целиком или отклоняется; предусмотреть preview, проверку версии проекта и единую отмену.
- **Не фиксировать SDK преждевременно.** Требования к событиям, параметрам, состоянию и задержке уточнить на реальных встроенных инструментах и эффектах.

## После MVP

1. Музыкальное редактирование: piano roll, MIDI-ввод, velocity, swing, automation, простой синтезатор.
2. Запись и сведение: аудиодорожки, мониторинг, компенсация задержки записи, fades, sends, EQ, компрессор.
3. Внешние плагины: сначала один формат; состояние, автоматизация, задержка и обработка отказов.
4. Продвинутая работа: time-stretch, tempo map, comping, sidechain, сложная маршрутизация.
5. Экосистема: SDK, модульный patcher, скрипты после стабилизации модели обработки.

## Открытые решения и риски

- Основная платформа первого прототипа: Linux; расширять матрицу после проверки ядра.
- UI-фреймворк выбрать после звукового прототипа, а не строить сразу несколько реализаций.
- Уточнить первый целевой сценарий: предложен workflow семплов и паттернов.
- Главный ранний риск — ещё не проверенный аудиодвижок; точные сроки пока не оценены.
- Ориентир каждого крупного этапа — возможность закончить и сохранить музыкальную работу, а не количество заявленных функций.
