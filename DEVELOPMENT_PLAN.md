# OxideDAW — план разработки

Обновлено: 2026-11-21. Первая платформа прототипа — Linux.

## Состояние реализации

- Cargo workspace: oxide-core, oxide-audio, oxide-dsp, oxide-midi, oxide-plugin-sdk, oxide-mcp, oxide-app.
- CLI перечисляет устройства, воспроизводит файл и зацикленный 16-шаговый паттерн из четырёх семплов.
- Декодирование mono/stereo выполняется до запуска потока. Частоты согласуются линейной интерполяцией.
- Транспорт поддерживает BPM, loop, one-shot, play/pause/stop; события имеют точные смещения внутри аудиоблока.
- Семплер выделяет восемь голосов на дорожку. Повторные удары перекрываются; при заполнении пула заменяется старейший голос.
- Stereo-микшер применяет velocity, master volume и финальное ограничение -1..1. One-shot доигрывает хвосты; stop очищает голоса.
- Аудиообработка не декодирует файлы, не выделяет память и не использует блокирующие операции.
- Формат проекта v3 сохраняет основной и именованные паттерны, четыре дорожки, темп, громкость, частоту и список тактов. Такты могут повторно использовать паттерн по ID. Проекты v1/v2 открываются и записываются в v3 при явном сохранении.
- `project-new`, `project-info`, `project-play` создают, открывают и воспроизводят сохранённый ритм. Внутренние ссылки на медиа относительные; внешние абсолютные. Загрузка допускает отсутствующие файлы; запуск воспроизведения сообщает дорожку и путь.
- Сохранение записывает и синхронизирует временный файл рядом с проектом, затем атомарно заменяет документ; создание нового файла атомарно отказывается от перезаписи.
- Нативный UI на eframe/egui: аппаратная панель ритма с линейкой перехода по шагам, браузер семплов, сетка 4×16, velocity, waveform, объёмные ручки семплера, транспорт, фейдер master volume со шкалой dB, отдельные L/R peak-метры, открытие/сохранение и общая история undo/redo. GUI запускается через `cargo run -p oxide-app --features gui -- gui [проект]`; редактирование паттерна, BPM и громкости передаётся в аудио как один ограниченный снимок состояния. Индикатор шага читает музыкальную позицию аудиопотока. Уровни накапливаются между блоками и чтениями UI без выделения памяти; audition семпла и сброс канала подключены к движку и истории.
- Команда `mcp` запускает локальный stdio-сервер. Инструмент `get_project_summary` читает снимок сохранённого проекта. SDK содержит начальные структуры.
- `project-export` использует общий движок для офлайн-рендера аранжировки или одного паттерна с хвостами семплов в новый стереофайл WAV на частоте проекта. В CLI доступны PCM 16 бит (по умолчанию), PCM 24 бит и IEEE float 32 бит.
- `set_arrangement` задаёт порядок тактов. Такт может ссылаться на основной паттерн, задавать собственную вариацию или содержать паузу. Изменение поддерживает undo/redo. Обычный `project-play` зацикливает основной паттерн. В GUI вкладка Arrangement задаёт последовательность тактов и переключает транспорт на её воспроизведение. `project-play --arrangement` зацикливает всю аранжировку и поддерживает seek по шагам нескольких тактов.
- Общие команды ядра меняют шаги по ID дорожки, BPM, master volume и ссылки на семплы. Пакеты атомарны; undo/redo хранит до 128 действий в памяти. CLI `project-edit` принимает JSON-команды и пакеты, поддерживает просмотр и явное сохранение. Дополнительные проверки покрывают откат ошибочных пакетов, ветвление и лимит истории, а также сохранение и повторное открытие через CLI.

Проверки: 45 тестов (включая CLI integration), rustfmt и clippy проходят. Дополнительно покрыты seek, смена BPM на границе шага и внутри шага, one-shot после смены темпа и переполнение очереди управления. Offline-тесты проверяют границы блоков, loop, отсутствие накопления округления, полифонию, pause/stop, velocity/stereo, one-shot хвосты и некорректные параметры. Дополнительно проверены сериализация, валидация, атомарное сохранение, защита от перезаписи, перенос папки и диагностика отсутствующего медиа. CLI, включая воспроизведение сохранённого stereo-проекта из другой рабочей директории, проверен через виртуальный ALSA `null` выход. Реальный аудиовыход и устойчивость на железе пока не проверены.

## Сценарий MVP

Открыть приложение → загрузить несколько WAV → собрать ритм → сделать короткую аранжировку → сохранить и повторно открыть проект → экспортировать WAV. Интерфейс и AI используют единые команды; изменение агента отменяется одним действием.

| Этап | Содержание | Критерий завершения |
| --- | --- | --- |
| Звуковой прототип | Устройства, WAV, громкость, start/stop | Стабильное воспроизведение на Linux |
| Музыкальное ядро | Транспорт, события, полифония | Паттерн играет без накопления временного дрейфа |
| Модель проекта | Дорожки, паттерны, медиа, команды | Сохранение и загрузка восстанавливают музыкальное состояние |
| Первый UI | Браузер семплов, step sequencer, транспорт, микшер | Ритм можно собрать без редактирования файлов |
| Законченный MVP | Arranger, WAV export, автосохранение | Трек можно создать, закрыть, открыть и экспортировать |
| AI-сценарий | Чтение состояния, пакетные команды | Изменения агента видны и отменяются одним действием |

## Архитектурные ориентиры

- Редактируемая модель проекта отделена от подготовленных данных аудиодвижка.
- UI и MCP используют общую валидацию и историю отмены. Пакеты команд применяются целиком или отклоняются.
- Декодирование, сеть, логирование, выделение и освобождение памяти выполняются вне аудиообработки. Ограниченные очереди должны иметь определённое поведение при переполнении.
- Музыкальное время согласует ticks, доли и samples; поведение seek, loop и смены BPM задаётся явно.
- Формат проекта имеет версию, устойчивые ID, относительные ссылки на медиа и атомарное сохранение.
- Rust обеспечивает безопасность памяти, но устойчивость аудио требует измерений на реальном оборудовании.
- Для первого UI выбран eframe/egui с OpenGL. Зрелый plugin SDK выбирается после проверки ядра на практических сценариях.

## Дорожная карта полноценной DAW

Цель на Linux — создать бит и инструментальные партии, собрать песню из
паттернов и аудио, записать исполнение, свести проект с автоматизацией,
повторно открыть его и экспортировать мастер и стемы. Ориентир для рабочих
процессов — Channel Rack, Piano Roll, Playlist, Mixer и Browser из
[руководства Image-Line](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/basics_workflow.htm).

Сейчас OxideDAW закрывает цикл «четыре семпла → ритм → последовательность
тактов → WAV». Главный разрыв — песня с несколькими независимо редактируемыми
паттернами, нотами и клипами. Приведённые ниже этапы описывают будущую работу.

### 0. Надёжность проекта и проверка звука

- [x] Периодические снимки восстановления для новых и сохранённых проектов.
  После прерывания приложение предлагает открыть последний снимок как
  отдельный проект. Исходный файл сохраняется, ссылки на медиа работают.
- [x] Переназначение отсутствующего медиа и сбор переносимого проекта.
  `project-pack` копирует семплы и сохраняет относительные ссылки. Тест
  сравнивает WAV до упаковки и после переноса папки.
- [ ] Проверка WAV, паттерна и аранжировки на физическом аудиовыходе Linux.
  Фиксировать устройство, частоту, буфер, длительность прогона и сбои.
- [x] CI для форматирования, тестов и Clippy на Linux.
- [ ] Воспроизводимые тестовые проекты для миграций, восстановления,
  рендеринга и проверки релизов.

**Критерий** — восстановить последний записанный снимок после принудительного
завершения и открыть перенесённую папку проекта с тем же звуком.

### Совместимость и MCP

- [ ] Экспорт .flp вести отдельно. Сообщать о потерях до записи и открывать

  .oxide.json.
- [ ] MCP сначала читает состояние проекта и транспорта. Затем — ограниченные

  Сохранение и экспорт выполняются явными командами.
- [ ] После стабилизации графа рассмотреть модульный patcher, расширенный SDK,

### Порядок ближайших изменений

1. Модель клипов и размещение паттернов в Playlist
   и проверка общего рендера.
2. Ноты, мелодический семплер и Piano Roll. Далее аудиоклипы и граф микшера.
3. Автоматизация после появления стабильных параметров. Запись после

Для пользовательских изменений проверять путь через UI или CLI, валидацию,
историю и save/reopen. Для звуковых изменений сравнивать live и offline на

виртуального выхода.
